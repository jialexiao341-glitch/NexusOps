# NexusOps：智慧商圈交易平台｜开发计划与测试验收

> 文档版本：重构版 v2.0 · 文档定位：**按什么顺序完成、怎样实验、何时算通过**  
> 需求：[项目需求规格说明](01_项目需求规格说明.md) · 技术：[系统架构与技术设计](02_系统架构与技术设计.md)

## 1. 实施策略

- 不一次性生成完整项目；每阶段先实现业务正确性基线，再进行性能优化与故障验证。
- 每周建议 40% 开发重构、30% 故障/压测、20% 原理和源码、10% 复盘。
- 阶段切换以验收为准。第 1～16 周为主线；第 17～20 周 RSI 为后续进阶，周数仅作建议。

## 2. 分阶段交付计划与验收

### 阶段一：高并发商户与秒杀（第 1–4 周）

**功能**：身份认证、商户/商品、商户详情与评分的最小数据模型、缓存、优惠券、同步正确性基线、限流、Redis Lua 预占原型。  
**关键原理**：ASGI、事件循环、MySQL 事务与行锁、唯一约束、Redis Key 设计、缓存穿透/击穿/雪崩、Lua 原子性。  
**故障实验**：热点缓存集中失效；Redis 短暂不可用；1000 并发请求抢 10 张券；异步路由插入阻塞 I/O。  
**验收**：在可复现的测试条件下，不超卖、不出现重复有效订单；请求重复提交安全；提供压测原始数据及至少两种技术实现的对照报告。

### 阶段二：交易与可靠消息（第 5–8 周）

**功能**：商户评价与回复、购物车、订单状态机、接单/备餐、模拟配送、模拟支付、超时关闭、RabbitMQ、Outbox、消费幂等、死信、对账；交付微信小程序点评/交易主流程及 Web 商家/平台基础后台。  
**关键原理**：事务边界、乐观/悲观锁、Publisher Confirms、ACK/NACK、至少一次交付、重试退避、幂等消费者。  
**故障实验**：Broker 停机后恢复；消费者提交后 ACK 前崩溃；同一支付回调重复 10 次；支付和取消并发；数据库死锁。  
**验收**：评价权限与订单合法状态迁移可测试；重试无重复业务副作用；事件可恢复发布；死信可追踪和人工处理；形成一次完整故障复盘。

### 阶段三：企业知识库与 RAG（第 9–12 周）

**功能**：文档上传、解析、Chunk、Embedding、索引、混合检索、Reranker、权限过滤、引用和增量更新；交付 Web 知识库管理界面。  
**关键原理**：BM25、向量相似度、HNSW、RRF、重排序、文档版本、元数据隔离、Gold Query 评测。  
**故障实验**：解析失败重试；索引构建中断；文档更新同时查询；越权检索；检索内容提示注入。  
**验收**：不少于 200 条人工核验的 Gold Query；比较至少四种检索配置并记录质量与延迟；文档版本可切换；越权测试全部通过。

### 阶段四：**纯手写 Agent Harness**（第 13–16 周）

**功能**：Model Adapter、Tool Registry、Agent Loop、Context Manager、Execution Journal、Checkpoint/Resume、审批门禁、Trace、评测；交付 Web Agent 工作台与小程序精简 AI 助手。  
**关键原理**：ReAct 与工具调用协议、状态机、事件日志、上下文预算、幂等副作用、有限重试、权限与策略。  
**故障实验**：执行 3 次工具调用后杀掉 Worker；外部工具超时；模型无限循环请求工具；审批前越权写操作；知识文本注入恶意指令。  
**验收**：不用 LangGraph 等 Agent 框架；不少于 100 条固定任务；关键越权/审批测试通过；断点恢复不重复执行已完成的副作用；任务 Trace 可核验。

### 阶段五：Agent RSI 自我改进（第 17–20 周，扩展阶段）

**功能**：收集任务轨迹和人工反馈，自动分析失败样本，生成 Prompt/Skill/工具策略候选；运行隔离评测，通过审批后灰度发布，支持一键回滚。  
**关键原理**：Recursive Self-Improvement（递归自我改进）的受控工程实现、实验设计、训练与评测数据隔离、过拟合控制、版本管理、策略回归与安全门禁。  
**故障实验**：候选策略只在已见任务上提升、在未见任务下降；新 Skill 越权调用工具；候选导致 Token 成本激增；发布后异常率上升；恶意反馈污染候选。  
**验收**：有完整的基线→候选→测试→审核→发布→回滚链路；在固定与未见测试集上记录收益和代价；安全门禁失败则不可发布；演示一次自动回滚或人工回滚。

> 阶段五属于 **16 周主线之后的可选进阶（建议另预留 4 周）**。先保证 Harness 稳定、评测基线可靠，再研究 RSI，避免让不可靠的 Agent 自动修改生产环境。

> **进度解释**：16 周按每周约 12–15 小时估计，仅供规划；是否进入下一阶段取决于上一阶段的验收结果，而不是时间到了就切换。

## 3. MVP 与范围管理

| 里程碑 | 必须完成 | 暂缓 |
|---|---|---|
| M1 交易正确性 | 商户/商品/评价基础、Redis 缓存、MySQL 秒杀基线 | 社交 Feed、复杂推荐 |
| M2 交易闭环 | 购物车、外卖订单、模拟支付/配送、团购核销、管理后台、消息可靠性 | 真实资金与骑手系统 |
| M3 知识服务 | 文档上传、版本、权限、混合检索、证据 | 大规模图谱自动构建 |
| M4 智能执行 | 手写 Loop、工具权限、Journal、Checkpoint、审批、Agent 评测 | 任意代码执行、微服务化 |
| M5 受控改进 | RSI 提案、隔离评测、审批、灰度与回滚 | 自动模型训练与无监督自修改 |

## 4. 必做实验清单

| 编号 | 实验 | 操作 | 需要证明的结论 |
|---|---|---|---|
| E01 | 竞争库存 | 固定库存 10，1000 并发购买 | 不超卖，数据库业务约束有效 |
| E02 | 缓存击穿 | 热点 Key 同时过期 | 可观察回源峰值及保护效果 |
| E03 | 缓存一致性 | 并发更新与读回填 | 不一致窗口可量化、可解释 |
| E04 | FastAPI 阻塞 | 混入 `time.sleep` 与同步 I/O | 正确理解事件循环与线程池 |
| E05 | 消息重复 | ACK 前杀掉消费者 | 同一业务事件不会重复生效 |
| E06 | 发布失败 | 停 Broker 再恢复 | Outbox 能补发且不丢业务事件 |
| E07 | 支付与取消竞争 | 同时触发回调与超时 | 订单状态合法、库存不重复释放 |
| E08 | RAG 对照 | BM25/Dense/Hybrid/Rerank | 评测指标与性能取舍可比较 |
| E09 | 文档更新 | 索引更新期间读查询 | 无混合版本引用，旧版/新版切换可控 |
| E10 | RAG 隔离 | 跨租户构造相似文档 | 越权检索不可达 |
| E11 | Agent 中断 | 模型/工具运行中杀进程 | 可恢复且不会重复外部副作用 |
| E12 | Agent 边界 | 超时、循环、恶意文档、绕审批 | 预算、权限和审批门禁生效 |
| E13 | RSI 过拟合 | 候选在开发集提升，在留出集下降 | 未见任务评测可阻断虚假提升 |
| E14 | RSI 策略回退 | 发布错误工具路由策略并触发告警 | 有版本记录且能安全回滚 |
| E15 | RSI 安全门禁 | 注入越权 Skill 或高风险 Prompt 候选 | 未经审批、未通过安全测试的候选不能上线 |

每份实验记录包括：**实验假设 → 环境和负载 → 复现脚本 → 观察指标 → 原始数据 → 根因 → 方案 → 复测结果 → 局限性**。

## 5. 量化验收标准

| 域 | 必须验证 | 指标/证据 |
|---|---|---|
| 交易 | 并发抢购不超卖、不突破限购、重复请求不重单 | 固定数据与并发脚本，违规数量为 0 |
| 缓存 | 热点失效和 Redis 故障可复现、可比较 | QPS、P95/P99、回源量和错误率对照 |
| 订单 | 支付/取消竞争只产生合法状态 | 状态事件和数据库断言 |
| 消息 | Broker 重启、重复投递、ACK 前宕机可恢复 | Outbox/Inbox 记录、死信和对账报告 |
| RAG | 四种检索策略有可复现评测；权限隔离 | ≥200 条核验 Gold Query、Recall/MRR/nDCG、越权为 0 |
| Harness | 不依赖 Agent 框架、工具越权拒绝、断点恢复 | ≥100 条 Gold Task、Trace、审批测试、副作用不重复 |
| RSI | 候选可以被拒绝、发布和回滚 | 留出集、差异报告、安全门禁、审批及回滚记录 |
| UI | 各角色能完成核心端到端操作 | 关键页面 E2E、弱网和重复点击测试 |

> 上述样本数量是项目初始验收建议值，实际质量目标应以正式基线和评测有效性为准；不要凭空承诺与硬件无关的生产 QPS。

## 6. 第一周可执行任务

1. 初始化 FastAPI、SQLAlchemy、Alembic、MySQL、Redis、Docker Compose、pytest。
2. 完成结构化日志、错误码、健康检查、统一事务依赖、基础身份和商户模型。
3. 完成商品和商户查询 API、索引与 Cache Aside 基线。
4. 设计优惠券、库存、订单、唯一键与业务不变量。
5. 用 MySQL 条件更新 + 同事务落单实现同步秒杀正确性基线。
6. 使用 Locust 注入并发，记录库存、重复订单、P95、吞吐和数据库负载。
7. 输出实验报告并决定是否进入 Redis Lua 优化。

## 7. 每阶段交付清单

- 可运行代码、`compose.yaml`、`.env.example`、迁移与种子数据。
- 单元/集成/E2E 测试、故障注入与压测脚本。
- 关键设计的 ADR（问题、候选方案、采用理由、故障边界）。
- 原始指标、失败原因、复测对照和已知限制。
- README：启动、演示、测试、系统范围和安全限制。

## 9. 总体验收与暂不实现事项

主线完成：消费者两条消费路径贯通，商家可接单及核销，平台能治理；消息故障可恢复；RAG 有可追溯证据；Harness 能安全恢复且不越权。进阶完成：RSI 能对失败样本提出候选、独立评测、审核发布并回滚。

**范围控制**：上线支付资质、真实配送调度、大规模社交与推荐、自动微调、无审批自修改均不属于当前验收条件。
