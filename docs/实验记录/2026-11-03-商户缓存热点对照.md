# 商户缓存热点对照（2026-11-03）

## 实验假设

同一商户缓存同时失效时，短期互斥锁可以减少完整详情查询的并发回源次数。

## 环境与方法

- 本机开发库 `nexusops`，只读取商户 3；Redis 为本机 Docker 开发实例。
- 每组 24 个线程同时开始，分别执行无锁 Cache Aside 与锁保护的缓存重建。键名使用随机实验标识，结束后仅删除本次生成的键。
- 每次完整详情回源人为加入 100 毫秒延迟，便于复现重建竞争；两组执行条件相同。
- 脚本：在 `backend` 目录运行 `$env:NEXUSOPS_ENV="dev"; uv run python -m experiments.cache_hotspot`。
- 度量的是缓存函数级别的完整详情回源和耗时，不含 HTTP、认证及每次请求的数据库状态校验；错误数为返回商户编号不符的数量，未捕获异常会导致脚本中止。

## 结论和局限

在本次人为延迟条件下，锁保护将完整详情回源从 23 次降为 1 次。等待超过 0.5 秒或 Redis 不可用时，请求会回源数据库；锁超时后原持有者不能覆盖新缓存。数据库状态校验仍发生在正常接口请求中。

仅进行了一次函数级对照，没有执行 HTTP 端到端负载、持续吞吐量、Redis 中断注入或并发更新一致性实验；24 个样本的尾延迟统计只用于观察，不可视作稳定性能结论。此前用户在界面验证过缓存写入与更新后刷新；Redis 停止期间查询的结果未在本记录中独立复核。
